# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Laravel 13 marketing/reservation site for **Tiflis**, a fictional Georgian restaurant in Nice (Côte d'Azur), France. Blade + Alpine.js + Tailwind CSS, with Livewire (v4) powering the two interactive pieces: the public table-reservation form and the admin back office. Auth scaffolding is Laravel Breeze (Blade stack).

The site is **bilingual, English-first** (`SetLocale::DEFAULT = 'en'`). All user-facing copy lives in `lang/en/site.php` and `lang/fr/site.php` — don't hardcode either into views. Restaurant facts (address, phone, hours, reservation rules) live in `config/restaurant.php`.

## Running locally (Docker / Sail)

```bash
./vendor/bin/sail up -d              # app, mysql, mailpit
./vendor/bin/sail artisan migrate --seed
./vendor/bin/sail npm install
./vendor/bin/sail npm run dev        # Vite with hot reload, or `npm run build` for production
```

- App: `http://localhost:8120` (port set by `APP_PORT` in `.env`)
- Mailpit UI (catches reservation confirmation emails): `http://localhost:8145`
- An admin user is seeded from `ADMIN_EMAIL` / `ADMIN_PASSWORD` (defaults: `admin@tiflis-restaurant.example` / `password`) — log in at `/login` to reach the dashboard at `/admin`.

Ports were deliberately chosen not to collide with sibling Sail projects on this machine (`cleaning_agency`, `pcn_boxing`, `healthy_life`, etc. — see their `.env` files for the ones already taken): `APP_PORT=8120`, `VITE_PORT=5190`, `FORWARD_DB_PORT=3350`, `FORWARD_MAILPIT_PORT=1045`, `FORWARD_MAILPIT_DASHBOARD_PORT=8145`.

To run app server + queue worker + log tailing + Vite together:

```bash
./vendor/bin/sail composer run dev
```

## Tests & linting

```bash
./vendor/bin/sail artisan test
./vendor/bin/sail pint          # code style (Laravel Pint)
```

`tests/Feature/{ReservationBookingTest,ReservationManageTest,GoogleBookingTest}.php` and `tests/Feature/Admin/{AdminAccessTest,ReservationManagerTest,MenuItemManagerTest}.php` (32 tests) cover the booking flow, capacity/overbooking enforcement (including under the Google path), the manage/cancel link, admin role gating, and the admin dashboard — on top of the stock Breeze auth/profile tests (minus registration, which is deleted). 57 tests total. Standard PHPUnit (not Pest) against the `testing` MySQL database (`phpunit.xml` sets `DB_DATABASE=testing`, `QUEUE_CONNECTION=sync`, `MAIL_MAILER=array` — mail is asserted with `Mail::fake()`/`assertQueued`, not actually sent). `GoogleBookingTest` mocks Socialite (`Socialite::shouldReceive('driver->user')->andReturn(...)`) and sets `config(['services.google.client_id' => 'fake-client-id'])` per-test to get past the "not configured → 404" guard — real Google credentials are never needed to run the suite. `Admin\DashboardOverview` doesn't have dedicated tests yet (it's read-only aggregation over the same `Reservation` queries already covered elsewhere) — add some if its KPI math changes.

**Landmine already hit once, worth knowing:** don't name a Livewire `#[Computed]` property (or any public property) `slots` — Livewire 4 ships a `SupportSlots` feature for content passed into `<livewire:component>...</livewire:component>` tags, and a component-level property/method named `slots` collides with its internal dehydration and throws `Call to a member function getName() on array` on the very first `Livewire::test()->set(...)` call (and would do the same over real AJAX requests). `ReservationForm::availableSlots()` is named that way for exactly this reason — don't rename it back to `slots`.

## Architecture

**Localisation:** `App\Http\Middleware\SetLocale` (appended to the `web` group in `bootstrap/app.php`) reads a `locale` session key and falls back to English. `GET /locale/{locale}` (`LocaleController::switch`) sets the session key; `<x-locale-switcher>` renders the EN/FR toggle in the nav.

**Public flow, one page:** `HomeController::index` loads `MenuItem::where('is_featured', true)` for the homepage teaser and renders `resources/views/page/home.blade.php`, which stitches together section partials from `resources/views/website/` (`hero`, `about`, `menu-preview`, `gallery`, `reservation`, `hours`). `MenuController::index` renders the full carte at `/menu` from all `MenuCategory::with('items')`. The shared chrome (head, nav, footer) is the anonymous component `resources/views/components/layouts/site.blade.php`, used as `<x-layouts.site>` — **anonymous Blade components must live under `resources/views/components/`, not `resources/views/layouts/`**; that's a landmine already tripped once during scaffolding (`layouts.site` 404'd until moved).

**Menu data model:** `MenuCategory` has many `MenuItem` (`menu_category_id`). Both carry `name_en`/`name_fr` (and items also `description_en`/`description_fr`) rather than using a separate translations table — simple enough for a single-restaurant menu, and it's what `MenuItem::name()`/`description()` and `MenuCategory::name()` read from based on `app()->getLocale()`. Seeded via `database/seeders/MenuSeeder.php` with a real (if illustrative) Georgian menu — khachapuri, khinkali, pkhali, mtsvadi, etc. — across six categories. Admin CRUD for items is `App\Livewire\Admin\MenuItemManager` at `/admin/menu-items` (category management itself has no UI yet — categories are seed-only; add one if the restaurant needs to reorganise the carte).

**Reservations, two-step + capacity-aware:** `App\Livewire\ReservationForm` (embedded on the homepage via `<livewire:reservation-form />`) is a two-step flow — step 1 (date, party size, a visual time-slot grid) then step 2 (contact details) — rather than one long form. Step 1 blocks the configured closed day (`config('restaurant.reservation.closed_day')`, currently Monday), enforces `min_hours_ahead`/`max_days_ahead`/`max_guests`, and **the room can't be oversold**: `Reservation::remainingSeats($date, $time)` sums non-cancelled `guests` for that slot against `config('restaurant.reservation.seats_per_slot')` (40), the time-slot buttons show remaining seats or render disabled once full, and `goToDetails()` re-validates capacity for fast feedback. There's no per-day service-hours override (e.g. Sunday's shorter hours in `config('restaurant.hours')` display copy aren't enforced in `ReservationForm::availableSlots()`) — add one if that divergence matters.

**Capacity enforcement is race-safe, not just optimistic:** the `goToDetails()`/step-1 check is a UX nicety — the actual authority is `Reservation::createWithCapacityCheck()`, which `save()` calls instead of a plain `Reservation::create()`. It takes a MySQL named lock (`GET_LOCK('reservation_slot:{date}:{time}', 10)`) before re-checking `remainingSeats()` and inserting, so two people booking the last seats in the same slot at the same instant can't both pass the check and jointly oversell it — the loser gets `null` back and `ReservationForm::save()` turns that into a normal `time` validation error (bounced back to step 1), not a 500. This only works because the app always runs on MySQL (dev and `phpunit.xml`'s `testing` DB both do) — `GET_LOCK`/`RELEASE_LOCK` are MySQL-specific, so don't port this model to another DB driver without swapping the locking mechanism too. On success it creates a `Reservation` (status `pending`, auto-assigned a random `manage_token` in `Reservation::booted()`) and sends `App\Mail\ReservationReceived` — a **queued** (`ShouldQueue`) markdown mail with a manage/cancel button, explicitly pinned to the booking request's locale via `Mail::to(...)->locale(app()->getLocale())->send(...)` since a queue worker processes it later under its own process locale, not the customer's.

**"Continue with Google" is a booking shortcut, not a login system:** it's unrelated to the admin auth above — there's no Google sign-in for the dashboard, and this doesn't create a `User` row at all. On step 1, `ReservationForm::continueWithGoogle()` re-validates date/time/guests (same rules as `goToDetails()`), stashes them in `session('pending_booking')`, and does `$this->redirect(route('google.redirect'))` — a real off-site navigation, since Livewire component state can't survive leaving the page. `GoogleBookingController::redirect()`/`callback()` handle the actual OAuth round-trip via `laravel/socialite`; the callback pulls `pending_booking` back out of the session, re-runs `Reservation::createWithCapacityCheck()` (so a slot that filled up during the OAuth detour is still caught), and on success sends the same `ReservationReceived` mail and redirects straight to `route('reservations.manage', ...)` with a `just_booked` flash flag (banner in `page/manage-reservation.blade.php`) — reusing that page as the confirmation screen instead of building a separate one. Bookings made this way have `phone` **null** (Google's default scopes don't include a phone number) and `source = 'google'` (vs `'manual'`); the admin reservations table shows a small Google "G" mark next to the guest's name for these. **The button auto-hides** when `config('services.google.client_id')` is blank (`ReservationForm::render()`'s `googleEnabled` var) — `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`/`GOOGLE_REDIRECT_URI` are blank in `.env`/`.env.example` by default, so out of the box nobody sees a broken button. To actually turn it on: Google Cloud Console → APIs & Services → Credentials → OAuth client ID (type "Web application") → set an authorized redirect URI matching `GOOGLE_REDIRECT_URI` (`{APP_URL}/auth/google/callback`, i.e. `http://localhost:8120/auth/google/callback` locally) → drop the client ID/secret into `.env`.

**Self-service manage/cancel:** `GET /reservations/{token}` (`ManageReservationController::show`, `page/manage-reservation.blade.php`) looks up a `Reservation` by its unguessable `manage_token` and shows status + details; `POST /reservations/{token}/cancel` sets status to `cancelled`, freeing those seats back into `remainingSeats()` for that slot. No auth needed — the token in the URL *is* the credential, same pattern as most email-based booking systems. There's no way to change the date/time/party size here, only cancel — if the restaurant wants self-service rescheduling later, that's new scope.

**Admin dashboard:** `App\Livewire\Admin\DashboardOverview` at `/admin` (route name `admin.dashboard`) is the landing page after login — KPI cards (today's reservations/guests, pending count, this-week count), a per-slot occupancy bar for today sourced from the same `seats_per_slot` capacity, and an upcoming-reservations list. It self-refreshes every 60s via `wire:poll.60s`. `Admin\ReservationManager` (`/admin/reservations`) adds search (name/email/phone), a status filter, and a date-range filter — all three are `#[Url]`-bound so filtered views are bookmarkable/shareable — plus a slide-over detail panel (`view($id)`/`closeDetails()`) instead of relying on inline row buttons. `Admin\MenuItemManager` (`/admin/menu-items`) groups items by category with counts; category management itself still has no UI (categories are seed-only — add one if the restaurant needs to reorganise the carte). All three (plus `DashboardOverview`) use `#[Layout('layouts.dashboard')]`, **not** `layouts.app` — `resources/views/layouts/dashboard.blade.php` is the real admin shell (dark sidebar nav, topbar with locale switcher + user avatar, light `stone-100` content area); Breeze's stock `layouts/app.blade.php` + `layouts/navigation.blade.php` + `resources/views/dashboard.blade.php` are still on disk from scaffolding but are dead code now — nothing routes to them (`/dashboard` just redirects to `admin.dashboard`). Don't resurrect them for admin pages; extend `layouts/dashboard.blade.php` instead.

**Auth model:** there is no public self-registration — `routes/auth.php` deliberately has no `/register` route, and `RegisteredUserController`/`auth.register.blade.php` were deleted rather than left dead (see `routes/auth.php`'s comment for why). Staff accounts are created only via `database/seeders/AdminUserSeeder.php` or `artisan tinker`. `/admin/*`, the legacy `/dashboard` redirect, and `/profile` all require `auth` + `verified`; `/admin/*` additionally requires the `admin` middleware alias (`App\Http\Middleware\EnsureUserIsAdmin`, registered in `bootstrap/app.php`), which checks `User::isAdmin()` (backed by `users.is_admin`) and `abort(403)`s otherwise. **`is_admin` is deliberately not in `User`'s `#[Fillable(...)]`** — it can only be set via `forceFill()`/direct attribute assignment in trusted server-side code (that's how `AdminUserSeeder` does it), never through mass assignment, so even if a registration form were reintroduced by mistake it couldn't self-grant admin. `tests/Feature/Admin/AdminAccessTest.php` locks this behaviour in (403 for a logged-in non-admin, 404 for `/register`, and a direct mass-assignment test on `User`).

**Images:** `public/images/` (hero, about, gallery) are real photos pulled from Wikimedia Commons (CC BY / CC BY-SA / CC0 — see each file's Commons page for attribution) as stand-ins, the same way the sibling projects use stock photography until the client supplies real ones. Swap them for actual restaurant photos before launch; if attribution-required photos stay in use, credit them somewhere (e.g. footer or an `/credits` note).

**Mail & queue:** `MAIL_MAILER=smtp` pointed at the `mailpit` container locally. `App\Mail\ReservationReceived` is `ShouldQueue` (`QUEUE_CONNECTION=database`), so it needs a worker — `compose.yaml` runs one as its own `queue` service (`php artisan queue:work --tries=3 --sleep=3`, same built image as `laravel.test`), so `sail up -d` alone is enough; there's no manual "remember to start the worker" step for local dev. If you ever run this outside Sail (e.g. a bare `php artisan serve`), start one manually with `php artisan queue:work` or the job just sits in the `jobs` table forever and no confirmation email goes out.

## Front-end conventions

- Brand palette is `wine-*` (deep Georgian-wine red/burgundy) and `gold-*` (warm amber) in `tailwind.config.js`. Headings use `font-display` (Playfair Display); body text uses Figtree.
- Shared button/section styles are `@layer components` classes in `resources/css/app.css` (`.btn-primary`, `.btn-ghost`, `.btn-gold`, `.section-eyebrow`, `.section-title`, `.card`).
- The nav (`<x-site-nav>`) is absolutely positioned with white/gold text over a dark backdrop — it assumes whatever sits behind it (hero image, or the dark banner atop `/menu`) is dark enough for light text to read. Any new page added to the public site needs a dark band up top, or the nav needs revisiting.
- The hours/location map is Google's classic `maps.google.com/maps?q=<lat>,<lng>&output=embed` endpoint (no API key needed), pinned to `config('restaurant.address.lat'/'lng')` — same approach as `~/projects/cleaning_agency` and `~/projects/pcn_boxing`.
